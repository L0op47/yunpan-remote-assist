- 项目代号：remote-assist；应用显示名：云畔

- 说明：本文档描述「儿子远程协助年迈父母安卓手机」的自研工具。它是完整设计文档（project 规模），后续将据此制定分阶段实施计划。

## 1. 背景

操作者（以下称「儿子」）的父母年迈，使用一台 vivo 系 iQOO 安卓手机。手机出问题时（找不到微信入口、误装广告 App、设置被改乱），儿子只能在电话里一步步指挥，效率低、体验差。

儿子自己的手机是一加（安卓）。他想要一个自己的工具：父母手机出问题时，在自己手机上直接看到父母屏幕并替他们操作，几分钟解决。此项目同时承担学习目标——作为 Android 开发、实时传输与网络安全的实践项目。

## 2. 目标与成功标准

目标：

1. 儿子在一加手机上发起对父母 iQOO 的远程协助会话：实时画面、点击/滑动、文字输入、返回/主页。
2. 父母端全程可见、可控：每次会话父母知情并确认；一次配置后，日常只需按一个大按钮。
3. 全链路零月费：不购买/不租用服务器，不改动任何路由器设置，不开放入站端口。
4. 只有儿子本人能发起连接（首次配对之后）。
5. （学习目标）分阶段实现，儿子亲手编写主要模块。

成功标准（验收）：

- 首次安装：儿子仅通过微信电话指挥，父母能在 ≤30 分钟内完成安装与全部授权（含重试）。
- 日常使用：父母来电 → 儿子发起 → 父母按提示点击（≤2 次）→ 10 秒内看到画面（网络正常时）。
- 会话质量：同城宽带下操作延迟体感 ≤300ms，画面宽度约 720–960px 可辨识。
- 成本：0 元/月。
- 安全：未配对设备无法建立会话；会话期间父母端有不可隐藏的可见提示与「立即停止」入口。

## 3. 非目标与反目标

非目标（明确不做）：

- iOS/iPadOS 控制端或被控端；PC 端。
- 音频通道（双方用微信/电话语音同步沟通）。
- 文件传输、剪贴板同步（后续可议）。
- 公网服务器、VPN、路由器配置、内网穿透。
- 应用商店上架（个人使用，APK 侧载分发）。

反目标（即使可行也不做）：

- 任何静默、隐藏、未经机主确认的远程控制。
- 绕过系统授权或利用漏洞获取更高权限。
- 允许任何已配对者之外的人连接。

## 4. 约束

技术约束：

- 被控端必须是 Android（iOS 不允许同类能力）；两端均为 Android。
- 远程控制依赖两项系统能力：MediaProjection 屏幕采集（每次会话需机主在系统弹窗中同意）与 AccessibilityService 手势注入（需在系统设置中手动开启）。二者均为系统可见、可审计的能力。
- 受保护页面（FLAG_SECURE，如银行、密码框）在系统层面无法被采集与注入——这是设计边界，不是缺陷。
- 父母设备具体型号/Android 版本待确认。开发目标 minSdk 26（Android 8.0），targetSdk 跟随最新稳定版；若真机低于 8.0 需重新评估。
- 通用性：App 面向通用 Android（标准系统 API，minSdk 26+），代码中不针对特定机型写分支；机型差异只体现在安装向导的步骤/文案按运行时检测的 Android 版本与厂商自适应，以及测试覆盖范围。承诺「已验证」的范围仅限操作者与父母的两台真机。
- 网络环境：双方家庭宽带（电信）+ 移动网络，IPv4 CGNAT 与 IPv6 并存；打洞成功率无法保证，必须有中继兜底。

使用与组织约束：

- 使用频率低（每月数次），单次约 10–40 分钟 → 拒绝任何按月计费的基础设施。
- 儿子无法到父母处现场操作；首次安装只能通过微信电话远程指挥完成 → App 必须自带「可语音指挥」的安装向导。
- 无自有服务器、无长期在线设备。
- 开发者即儿子本人（学习项目），单人、业余时间。
- 开发联调设备：控制端用一加真机；被控端用一台旧红米 Note 10（版本待通电确认，满足 minSdk 26 即可）。红米可覆盖 MediaProjection、无障碍、前台服务的主线开发；vivo/OriginOS 的保活与权限差异只能在父母真机上最终验证。

## 5. 方案取舍（Approaches）

方案 A：使用现成工具（向日葵/ToDesk/RustDesk/vivo 自带远程协助）。

- vivo 自带功能只支持 vivo/iQOO 作为控制端（儿子是一加），排除。
- 第三方工具可用，但依赖其服务器与免费策略，界面无法按老人习惯定制，也不能满足学习目标。
- 结论：仅作为开发期间的应急兜底，不作为本项目方案。

方案 B：自研协议 + 自购 VPS 中继（WebSocket 转发）。

- 简单直接、学习价值高；但需要每月 20–30 元的 VPS 与长期运维，对每月仅用几次的场景不划算。
- 结论：排除。保留为未来可选的可靠性升级路径（自建 TURN）。

方案 C（采用）：WebRTC 作传输管 + 自研应用层协议 + 免费公共基础设施。

- WebRTC 库（libwebrtc）自带 ICE/STUN/TURN 客户端与 DTLS 加密：两端优先打洞 P2P，失败自动经 TURN 中继，全程零服务器运维。
- 信令只是少量文本（SDP/ICE），走免费公共 MQTT broker。
- STUN 用免费公共服务；TURN 用免费公共服务（如 Metered Open Relay），地址可配置、可更换。
- 应用层协议（画面分片、输入事件、配对认证、会话状态机）完全自研，学习价值保留。
- 未来若需更高可靠性：把 TURN 换成自建，仅改配置，代码不变。
- 风险：公共服务的可达性/限额不受控 → 多地址配置 + 实测矩阵缓解（见 §11）。

子取舍：

- 视频编码：v1 用 JPEG 帧（简单、可调试）；v2 升级 H.264（MediaCodec 硬编硬解，带宽/画质更优）。
- 控制端形态：原生 Android App（否决 Web 端；两端同栈，学习收益最大）。
- 数据通道：v1 合并为单一可靠有序 DataChannel（实现简单）；v2 将视频拆到无序不可靠通道以降低延迟。

## 6. 总体架构

组件：

- `controller`：控制端 App（一加）。
- `agent`：被控端 App（iQOO）。
- `core`：共享 Kotlin 库（协议编解码、配对/加密模型、公共配置）。
- 公共基础设施（不归我们运维）：MQTT broker（信令）、STUN、TURN。

关系（文字图）：

```
[controller] --MQTT/TLS（信令）--> (公共 MQTT) <--MQTT/TLS（信令）-- [agent]
[controller] <==== WebRTC DataChannel（P2P 直连 或 经公共 TURN 中继）====> [agent]
```

- 单一 Gradle 工程，模块：`:app-controller`、`:app-agent`、`:core`。
- 语言 Kotlin；UI 用 Jetpack Compose；协程 + Flow。
- 包名草案：`dev.remoteassist.controller` / `dev.remoteassist.agent`（可改）。

## 7. 被控端（Agent）设计

### 7.1 安装与首次授权向导（电话可指挥）

- 六步向导，每步一张大卡片：标题（「第 N 步 / 共 6 步」）、一句大白话解释、一个超大按钮；字号 ≥24sp。
- 每步按钮直达对应系统页面（如 `ACTION_ACCESSIBILITY_SETTINGS`），并附该页面的实拍截图示意。
- 自动检测完成状态（无障碍是否开启、电池优化是否豁免；自启动状态检测不到则提示自检），完成项打勾。
- 通用性设计：向导步骤按运行时检测的 API 级别动态增减（如 Android 13+ 侧载应用多「允许受限设置」一步；通知运行时权限仅 Android 13+ 存在），厂商特有页面（如 vivo 自启动）提供文字路径与「在设置中搜索」兜底指引，不写死单一机型。
- 微信传 APK 常被拦截：安装指南提供备用分发（蓝奏云链接/QQ 传输），写入 §附录与 App 帮助页；安装时若 vivo 弹「安全检测/风险提示」，引导选择继续安装。
- 分发采用自签名 keystore 签名的 release APK，签名文件离线保管（换签名会导致无法覆盖升级）。

步骤草案：

1. 安装 APK（允许未知来源）→ 2. 通知权限 → 3. 开启无障碍服务 → 4. 关闭电池优化 → 5. 允许自启动/后台高耗电（vivo 特定路径，配截图）→ 6. 生成 8 位配对码（念给儿子）。

- 配对码：8 位数字，大字显示，有效期 10 分钟，可随时重生成；用于 §9.4 的一次性配对仪式。
- 版本更新（第一版范围决定）：MVP 不做应用内自动更新；新版本通过微信/蓝奏云重新分发、电话指挥覆盖安装（每次约 10–20 分钟；固定签名保证可覆盖升级）。内置更新器（REQUEST_INSTALL_PACKAGES + 版本检查 + 下载 + 签名校验）列为 M6 之后的可选增强——且它本身也必须先经一次手动安装才能到达。

### 7.2 会话流程

1. 常驻前台服务维持 MQTT 订阅（见 §7.5）。
2. 收到经签名的连接请求 → 全屏弹出求助页（大绿按钮「接受帮助」、大红按钮「拒绝」）。
3. 接受 → 系统录屏授权弹窗（Android 14+ 每次会话都弹出；提示父母在弹窗中选「整个屏幕」）→ 同意。
4. 进入会话界面：全屏、「正在被远程协助」状态不可隐藏、常亮（FLAG_KEEP_SCREEN_ON）、大红「立即停止」按钮；同时建立 WebRTC 会话并开始采集。
5. 结束（任一方或断线超时）→ 释放录屏、关闭会话界面，回到常驻状态（默认不保持录屏待命）。

### 7.3 采集与编码

- v1：MediaProjection + VirtualDisplay + ImageReader（RGBA_8888），缩放到宽度 ≤960px，JPEG 质量 60，目标 6–10 fps；单帧典型 40–120KB。
- v2：MediaCodec H.264（encoder surface 模式，VirtualDisplay 直接输出到编码器），目标码率 0.8–2Mbps 自适应，支持按需关键帧。
- 屏幕旋转：监听显示变化，重建采集管线（M5 处理）。

### 7.4 输入注入

- 点按/长按/滑动：`AccessibilityService.dispatchGesture(GestureDescription)`；坐标使用被控端当前屏幕绝对像素；点击时长 60ms，滑动按距离插值。
- 全局键：`performGlobalAction`（BACK / HOME / RECENTS）。
- 文本：定位焦点可编辑节点，`ACTION_SET_TEXT` 整段替换；不支持时提示（v2 再研究 IME 注入方案）。
- 限制：系统安全弹窗、部分厂商特殊界面可能无法注入；如实记录为已知边界。

### 7.5 保活与可靠性

- 常驻前台服务（`START_STICKY`；ForegroundService 类型按 targetSdk 规则声明，侧载场景可用 `specialUse`），会话期间另起 `mediaProjection` 类型服务。
- 开机自启：`BOOT_COMPLETED` receiver 拉起服务。
- WorkManager 周期心跳（≥15 分钟）检测并恢复 MQTT 连接。
- 厂商白名单：向导第 5 步引导 vivo 自启动与后台耗电设置。
- 降级路径：若进程被系统杀死、收不到请求 → 儿子打电话 → 父母点击桌面「帮爸妈」图标 → 按大按钮「让儿子帮我」→ App 前台恢复连接并通知儿子。此路径必须一句话能说清，写进父母端帮助卡（桌面快捷方式/纸质卡片模板）。

## 8. 控制端（Controller）设计

- 设备页：已配对设备列表（支持多台，如爸、妈各一台），显示名称与在线状态；「添加设备」→ 输入 8 位配对码。
- 会话页：视频渲染层 + 悬浮工具条（返回、主页、最近任务、键盘、结束）；手势直通（单指点击/滑动；双指滚动列入 v2）。
- 键盘：隐藏文本框输入整段文字，点「发送」注入（不做逐键同步）。
- 状态提示：等待父母确认 / 打洞直连 / 经中继 / 重连中；质量指示：帧率、估算延迟、当前链路。
- 会话日志：时间、链路类型、平均帧率/码率、错误事件，可导出文本，方便远程排障。

## 9. 传输、协议与安全

### 9.1 信令（MQTT）

- 公共 broker 默认 `broker.emqx.io:8883`（TLS）；配置中提供 broker 列表可替换（如 mqtt.eclipseprojects.io 等），以实测可达为准。
- 配对阶段：agent 订阅 `pra/pair/<8位配对码>`；controller 向该主题发送以配对码派生 PSK 加密的握手；双方交换长期公钥与设备名；随后迁移到由配对结果派生的长期主题 `pra/<topicId>/sig`（topicId 为随机 128 位，配对时确定）。
- 会话信令：`hello / offer / answer / ice / ping / bye`，JSON 编码，QoS1。
- 配对后的所有信令消息附带 ECDSA P-256 签名；agent 只响应已配对 controller 的请求。

### 9.2 ICE 配置

- STUN 候选（以实测为准）：`stun.l.google.com:19302`、`stun.miwifi.com:3478`、`stun.chat.bilibili.com:3478`。
- TURN 候选：Metered Open Relay（`openrelay.metered.ca`，80/443，UDP/TCP），凭据按公共服务当前要求；可配置替换。
- 策略：先 P2P，失败自动回退 TURN；`iceTransportPolicy` 默认 `all`，设置中可强制「仅中继」。

### 9.3 应用协议（DataChannel 上）

- v1：单一可靠有序通道，标签 `app`。
- 消息 = 1 字节类型 + 固定头 + 载荷；视频帧分片 ≤12KB，含 frameId / chunkIndex / chunkCount；收到按 frameId 组帧，丢弃过期与不完整帧。
- 类型草案：`HELLO`、`SCREEN_INFO`（宽高/旋转/dpi）、`VIDEO_CHUNK`、`INPUT_TAP/SWIPE/LONGPRESS`、`KEY`、`TEXT`、`PING/PONG`、`BYE`。
- 背压：发送端监测 SCTP `bufferedAmount`，超过阈值时丢视频帧（输入事件不丢、不阻塞）。

### 9.4 安全模型

- 长期身份：两端在 Android Keystore 生成 EC P-256 密钥（不可导出）。
- 配对仪式（一次性，电话中进行）：8 位配对码 → PBKDF2-HMAC-SHA256（≥150k 迭代）派生 PSK → AES-GCM 加密公钥交换；配对码 10 分钟有效、限次数重试；配对成功后码作废。
- 会话信令签名防伪造；WebRTC DataChannel 自带 DTLS 加密；公共 MQTT/TURN 只作信使与导管，看不到内容。
- 威胁模型：攻击者可监听/篡改公共 MQTT 与 TURN；配对窗口之外且无长期密钥时无法建立或冒充会话。配对窗口期的主动 MITM 需同时拦截并猜中 8 位码，按个人使用场景可接受；后续可升级 SPAKE2/OPAQUE。
- 机主可见性：录屏系统指示 + 常驻通知 + 全屏会话界面 + 一键停止，均设计为不可绕过。

### 9.5 性能与稳定性预期（估算，待 M1/M3 实测校验）

- 端到端画面延迟：P2P 直连约 100–200ms；经中继约 300–600ms（取决于中继位置与线路）。远程协助类操作（找设置、关弹窗、点按钮）在 ≤500ms 下可接受。
- 帧率：P2P 下 v1 JPEG 目标 6–10fps；中继视带宽降至 3–5fps 或降低画质。
- P2P 成功率（行业经验范围，非对具体线路的承诺）：家宽 ↔ 家宽约 70–90%；移动网络 ↔ 家宽约 40–70%；双方均在移动网络时更低。双方都有可用的 IPv6 时成功率提升。对称 NAT 与运营商 CGNAT 是主要失败原因。真实比例以 M3 的实测矩阵（Wi-Fi × 4G × 5G 组合）为准。
- 信令（公共 MQTT）只在连接建立与唤醒时需要，消息量极小；broker 故障时降级为「父母手动打开 App」路径，不阻塞既有会话。
- 免费公共 TURN 是整条链路最弱一环（共享、无 SLA、可能被限速或线路绕远），仅在打洞失败时使用。所有公共服务地址可配置替换；未来可换自建 TURN（改配置，不改代码）。
- JPEG 每帧独立编码：丢包只损失单帧，不产生后续花屏，弱网鲁棒性优于帧间编码。
- 参照系：向日葵/ToDesk 等商业工具因自有服务器，典型延迟约 100–250ms。本方案在 P2P 直连时与其相当，被迫走免费中继时低于其体验——这是零月费约束下的已知权衡。

## 10. 分阶段实施（MVP 路线）与学习目标

总体规模：单人业余开发，MVP（M0–M4）约 6–10 周；M5–M6 另计。以学习节奏为准，不承诺工期。每个里程碑可独立验收，按序推进。

- M0 工程骨架（1–2 天）：Gradle 多模块、两端 Compose 空壳、MQTT 连通性 Demo。
  学习：工程结构、MQTT 基础。
- M1 画面链路（最高风险先验证）：信令先用「手动复制粘贴 SDP」调试模式，打通 JPEG 采集 → 分片 → DataChannel → 解码显示。
  学习：MediaProjection / ImageReader、WebRTC 基础（PeerConnection / DataChannel / ICE）。
  验收：同一 Wi-Fi 下两机互见画面 ≥5fps。
- M2 输入链路：点按/长按/滑动/返回注入。
  学习：AccessibilityService、坐标系与手势。
  验收：控制端操作被控端完成一次真实任务（如打开微信 → 进入设置）。
- M3 自动信令与配对：MQTT 信令、配对仪式、长期密钥、会话授权弹层。
  学习：密钥学基础（Keystore、PBKDF2、签名）、MQTT 主题设计。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| vivo/OriginOS 杀后台，MQTT 断连收不到请求 | 无法一键发起 | 前台服务 + 自启动 + 心跳 + 白名单向导；降级路径（电话 → 点桌面大按钮）；每周自检提醒 |
| 公共 TURN/MQTT 失效或被限流 | 打洞失败时无法连接 | 多地址配置、运行时切换；紧急时可用第三方远程工具顶替；未来自建 TURN（仅改配置） |
| 打洞成功率低于预期（CGNAT/对称 NAT） | 依赖中继，质量下降 | 实测矩阵（Wi-Fi × 4G × 5G 组合）；设置「仅中继」开关 |
| Android 版本差异（录屏令牌、通知权限、前台服务类型） | 兼容性问题 | 以真机为准开发；权限声明按 targetSdk 规范；测试覆盖 API 26 至最新 |
| 无障碍注入被厂商系统限制 | 无法操作部分界面 | 真机验证；失败时退化为「只看屏幕 + 语音指挥」（天然兜底） |
| 微信传 APK 受限 | 安装受阻 | 蓝奏云链接/QQ 传输等备用通道写入安装指南 |
| 老人误触/担忧 | 拒绝使用 | 全流程可见、大红停止按钮、界面用语通俗（「儿子」而非「协助方」） |
| 配对窗口期 MITM | 首次配对被劫持 | 8 位码 + 10 分钟窗口 + 限次；威胁模型说明；后续 SPAKE2 |
